# 2026-11-11: 모델 ROS 분리와 실물 MoveIt 환경 정리

이 페이지는 현재 workspace에서 수행한 변경과 검증 범위를 기록합니다.
최신 실행 절차는 [시뮬레이션 집기](grasp-pipeline-guide.md),
[실물 MoveIt](piper-hardware-moveit.md), [실행 환경](piper-runtime.md)을 따릅니다.

## 1. BT와 모델 ROS 인터페이스 분리

역할별 BT 노드와 실제 메시지 Blackboard 연결을 구성하고, Nav2 형식의 헤더·CPP와
플러그인 라이브러리로 정리했습니다. SAM·GraspGenX ROS bridge는 모델별 패키지로
나누고 관측·점군·후보 선택·MoveIt 상태 관리는 grasp pipeline에 유지했습니다.

| 패키지 | 현재 책임 |
|---|---|
| rwh_beyond_sam3_bridge | `/segment_image`, `/sam3/health` |
| rwh_beyond_graspgenx_bridge | `/infer_grasps`, `/graspgenx/health` |
| rwh_beyond_grasp_pipeline | 관측·점군·선택·계획/장면 상태·MoveIt 호출 |
| rwh_beyond_model_utils | wire·배열·메시지 변환 공통 코드 |
| rwh_beyond_grasp_bridge | 이전 import/실행 명령 호환 |

기존 분리 작업은 `rwh_beyond`의 `0c352bb`, `ros_runner`의 `6a2a425`까지
push된 상태에서 이어졌습니다. 이후 실물 환경·설정·문서 변경은 이번 후속 작업에 포함됩니다.
최종 커밋 식별자는 각 저장소의 Git 이력에서 확인할 수 있습니다. 상세는 [모델별 bridge 문서](model-bridges.md)를 참고하세요.

## 2. 새 ROS 컨테이너와 CAN

호스트에서는 `can0`가 UP·1 Mbps였지만 이전 ROS 컨테이너의 slirp4netns에서는
보이지 않았습니다. SocketCAN은 `/dev` 파일이 아닌 네트워크 인터페이스입니다.

기존 writable layer를 이미지로 보존하고 `moma_mj_lab_1.1.2_hostcan`을 host
네트워크로 생성했습니다. `/root/ros2_ws`를 빈 볼륨으로 덮어쓰지 않았으며,
GPU·GUI·기존 코드/설치 결과를 유지했습니다. 모터나 runner는 자동 시작하지 않습니다.

호스트 `ros2-docker` 저장소에 다음을 추가했습니다.

- `scripts/snapshot-piper-dev.sh`: 이미지·컨테이너 메타데이터 보존
- `start-piper-dev.sh`: host network·GPU/GUI·CAN 소켓 검사
- `scripts/migrate-piper-models.py`: 두 모델 네트워크 전환·기존 컨테이너 보존

초기 비구동 시험에서 CAN 프레임 15,200개를 5초간 수신했고 당시 호스트 CAN
전송 카운터는 0, bus error는 0이었습니다. 소프트웨어 회귀는 78개·하위 검사 7개,
C++ BT 3개 테스트 묶음이 통과했습니다. 이는 이후의 실물 driver 통신까지
포함해 영구적으로 CAN 송신이 없었다는 뜻은 아닙니다.

## 3. 모델 네트워크 전환과 실제 추론

기존 두 모델은 이전 ROS 컨테이너 네트워크에 남아 있었고 새 ROS 컨테이너의
`check_ready`가 GraspGenX deadline으로 실패했습니다. 원본을 중지·이름 변경해
보존한 뒤 모델 이미지·checkpoint·캐시·GPU 설정을 유지해 새 네트워크로 옮겼습니다.

두 모델의 bind 주소는 host loopback입니다. ZMQ endpoint는 기존처럼
SAM 5567, GraspGenX 5566입니다. 원격 서버 배포나 통신 포맷 변경은 하지 않았습니다.

새 ROS 컨테이너에서 health와 실제 모델 ROS Action을 확인했습니다.
**이전 시뮬레이션에서 저장한 RGB-D**를 사용해 SAM 객체 1개·mask 2,783픽셀,
GraspGenX 후보 20개를 약 1.45초에 받았습니다. 실물 카메라 관측이나 로봇 이동 시험은 아닙니다.
[원시 결과](validation/hostcan-model-network-2026-11-11.json)를 참고하세요.

## 4. 실물 MoveIt 초기 구성과 발견한 설치 문제

공식 실물 driver를 사용하며 `can0`, agx_gripper, 자동 enable 꺼짐,
SDK speed_percent=10, 실제 관절 피드백, RViz를 runner에서 구성했습니다.

첫 기동 검사에서 다음을 수정했습니다.

- 오래된 MoveIt/description CMake 캐시와 symlink가 이전 MuJoCo 내부 경로를 참조함
- control gate 실행 파일의 설치 경로·실행 권한 문제
- 공식 실물 SDK `pyAgxArm`과 python-can 누락
- 빈 firmware override가 잘못된 ROS launch 인자로 전달되는 문제

기존 build/install 결과는 `.piper-build-backup`에 보존하고 공식 저장소 경로로
재빌드했습니다. pyAgxArm 1.0.0의 확인 commit은
`d90e234ba8e408cfa964b38aa9120b3131fc9f85`입니다.

실제 driver·MoveIt·RViz 기동과 6축·그리퍼 피드백을 확인했고 펌웨어는
`S-V1.7-3`으로 보고됐습니다. 해당 검증에서는 enable/trajectory 실행을 호출하지 않았습니다.
실측 joint3가 모델 상한보다 양수여서 plan-only 요청은 거부됐습니다.
[초기 실물 검증 기록](validation/piper-hardware-moveit-2026-11-11.json)에 실패를 포함했습니다.

## 5. 실물·시뮬레이션 MoveIt 설정 통일

실물 TCP가 0이고 시뮬은 Z +142.5 mm인 차이, 활성 planner 구성,
점군 self-filter/Octomap와 실행 시간 여유 차이를 확인했습니다.
실물 `piper_hardware.py`에서 시뮬 계획 baseline을 사용하도록 구성했습니다.

- TCP Z +0.1425 m, OMPL, 같은 KDL·관절 제한·controller Action 이름
- 같은 점군 max_range/subsample/padding/update rate, Octomap frame/resolution
- 같은 RViz 파일과 실행 시간 여유 설정
- 실물 CAN·피드백·모터/티칭·control gate와 `use_sim_time=false` 유지
- 시뮬 D405 mount는 실제 장착이 확인되지 않아 실물 기본값에서 제외

같은 카메라 모델을 선택하면 평가된 MoveIt 파라미터가 clock 외에 동일한 것을
확인했습니다. 설정 검사 18개·하위 검사 12개와 문서 strict 빌드가 통과했습니다.
CAN driver를 제외한 ROS domain 172에서 합성 상태로 arm/gripper controller 활성화,
RViz MotionPlanning 초기화와 OMPL plan-only 결과(6개 trajectory point)를 확인했습니다.
초기 병렬 controller spawner 대기 문제는 단일 spawner의 순차 구성으로 정리했습니다.
[설정 통일 검증 기록](validation/piper-moveit-parity-2026-11-11.json)을 참고하세요.

**설정 통일 후의 실물 이동은 검증하지 않았습니다.** joint3·그리퍼 raw feedback의
범위 초과는 유지되며, 제한 확대·피드백 clamp·임의 영점 재설정을 적용하지 않았습니다.

## 6. 현재 실행 이름과 지원 범위

| runner | 현재 동작 |
|---|---|
| piper_moveit | 실제 CAN driver + MoveIt + RViz |
| piper_moveit_sim | 현재 workspace에 남은 실물 runner의 기존 이름 |
| piper_sim | MuJoCo + MoveIt, BT가 통합 RViz를 소유 |
| bt_demo_sim | piper_sim 의존 + grasp pipeline + BT navigator + RViz |

이 이름은 현재 `ros_runner/config/runners.yaml` 기준입니다. 이전 기록에서
`piper_moveit_sim`이 MuJoCo를 가리켰던 것과 구분하세요.

시뮬레이터에는 티칭 모드/종료 서비스가 없으므로 BT에 티칭 종료를 추가하지 않았습니다.
실물 공식 `/exit_teach_mode`에는 원점 이동·모터 재활성화가 포함됩니다.
`/move_home`의 Empty 응답이나 성공 로그만으로 실측 도달을 판정할 수 없습니다.
실물 절차에서는 제어 모드·모터 상태·실측 관절·계획 결과를 구분해 확인합니다.

전체 grasp coordinator는 여전히 시뮬레이션 전용입니다. 실물 카메라·보정 TF,
실물 준비/접촉/부착/리프트 검증은 남은 작업입니다. 실물 MoveIt 실행 가능 여부와
전체 집기 BT의 실물 지원 여부는 별개입니다.
