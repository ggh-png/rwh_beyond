    GPU 추론 서버 운영¶

    SAM 3와 GraspGenX는 ROS 컨테이너와 분리한 GPU 프로세스로 실행합니다. 서버에서 모델을 준비한 뒤 로봇 PC의 SSH 터널·ROS bridge를 연결합니다. 아래 Docker 명령은 GPU 서버 호스트에서 실행합니다.

    배포 모델 컨테이너 생성¶

    /home/ggh/RWH/beyond의 20261117 배포 아카이브를 받은 경우 이 절을 사용합니다. 이미지 불러오기를 먼저 수행합니다. 다른 GPU 호스트에 복사했다면 cd 경로를 실제 배포 폴더로 바꿉니다. compose.models.yaml과 scripts/models.sh는 이 배포 폴더에 포함된 파일입니다.

    서버용 한 줄 생성 명령 — 모델 이미지가 이미 로드돼 있으면 다음을 실행합니다. GraspGenX·SAM 3 두 컨테이너를 함께 생성·시작합니다.

    # 배포 파일과 설정이 있는 디렉터리로 이동
cd /home/ggh/RWH/beyond && CONTAINER_ENGINE=docker ./scripts/models.sh start

    # 배포 파일과 설정이 있는 디렉터리로 이동
cd /home/ggh/RWH/beyond && CONTAINER_ENGINE=podman ./scripts/models.sh start

    로봇 컨테이너는 로봇용 한 줄 생성 명령을 사용합니다. 다음은 이미지 로드부터 Compose로 시작하는 대안 절차입니다.

    # 배포 파일과 설정이 있는 디렉터리로 이동
cd /home/ggh/RWH/beyond
# GraspGenX·SAM 3 이미지 아카이브를 로컬에 불러오기
docker load --input rwh_beyond_models_20261117.tar.gz
# GraspGenX 이미지에 프로젝트 고정 이름 등록
docker tag docker.io/rwh_beyond/graspgenx:20261117 rwh_beyond_graspgenx:20261117
# SAM 3 이미지에 프로젝트 고정 이름 등록
docker tag docker.io/rwh_beyond/sam3:20261117 rwh_beyond_sam3:20261117
# Compose 설정과 환경변수가 올바르게 적용되는지 확인
docker compose -f compose.models.yaml config
# 지정한 모델 컨테이너를 생성하고 백그라운드 실행
docker compose -f compose.models.yaml up -d
# 모델 서비스의 실행·정지 상태 확인
docker compose -f compose.models.yaml ps -a
# 지정한 모델 서비스의 최근 로그 확인
docker compose -f compose.models.yaml logs --tail 100 sam3 graspgenx

    직접 docker run으로 생성¶

    위 helper 또는 Compose 대신 직접 Docker 명령으로 생성하려면 모델별로 아래 한 줄을 실행합니다. 이는 배포본 scripts/models.sh의 Docker 생성 옵션과 같습니다. 같은 이름의 컨테이너를 두 방식으로 중복 생성하지 않습니다.

    이미지 이름 명령어
    GraspGenX 서버 # GPU·5566 포트를 연결해 GraspGenX 서버 생성·실행
    docker run -d --name rwh_beyond_graspgenx --restart unless-stopped --shm-size 256m --gpus all -p 127.0.0.1:5566:5566 -v rwh_beyond_graspgenx_cache:/data/cache -v rwh_beyond_graspgenx_logs:/data/logs rwh_beyond_graspgenx:20261117
    SAM 3 서버 # GPU·5567 포트를 연결해 SAM 3 서버 생성·실행
    docker run -d --name rwh_beyond_sam3 --restart unless-stopped --shm-size 256m --gpus all -p 127.0.0.1:5567:5567 -v rwh_beyond_sam3_cache:/data/cache -v rwh_beyond_sam3_logs:/data/logs rwh_beyond_sam3:20261117

    로봇용 생성·접속 명령과 wsyoon_data 마운트는 컨테이너 생성 방법을 참고하세요. 서버 내부 셸은 docker exec -it rwh_beyond_graspgenx bash 또는 docker exec -it rwh_beyond_sam3 bash로 접속합니다.

    Podman에서는 GPU CDI를 준비한 뒤 배포 helper를 사용합니다.

    # 배포 파일과 설정이 있는 디렉터리로 이동
cd /home/ggh/RWH/beyond
# GraspGenX·SAM 3 컨테이너를 함께 생성·시작
CONTAINER_ENGINE=podman ./scripts/models.sh start
# 두 모델 컨테이너 실행 상태 확인
CONTAINER_ENGINE=podman ./scripts/models.sh status

    가중치는 이미지에 포함돼 있으며 캐시·로그만 named volume으로 보관합니다. 컨테이너 생성 시 이미지의 기본 서버 명령이 실행됩니다. 가중치 로딩 후 다음으로 확인합니다.

    # GraspGenX 서버에 실제 health 요청 전송
docker exec rwh_beyond_graspgenx python /opt/deploy/scripts/health_check.py \
  --endpoint tcp://127.0.0.1:5566
# SAM 3 서버에 실제 health 요청 전송
docker exec rwh_beyond_sam3 python -c \
  "from wire import request; print(request('tcp://127.0.0.1:5567', {'action': 'health'}, timeout=5))"

    Podman이면 docker exec를 podman exec로 바꿉니다. 배포 helper의 CONTAINER_ENGINE=docker ./scripts/models.sh health로 두 모델을 함께 검사할 수도 있습니다. 재시작·종료는 기존 컨테이너를 대상으로 수행합니다.

    # 생성돼 있는 정지 컨테이너 시작
docker start rwh_beyond_graspgenx rwh_beyond_sam3
# 실행 중인 모델 컨테이너 종료
docker stop rwh_beyond_graspgenx rwh_beyond_sam3

    이 배포본은 GraspGenX 5566·SAM 5567을 사용하며 호스트 loopback에만 공개합니다. 다른 로봇 PC에서 접속할 때는 SSH 터널을 준비하고 runner의 모델 연결 설정을 맞춥니다. 다음 절은 배포 이미지가 아닌 저장소 소스에서 이미지를 빌드하는 방법입니다. 서비스 이름과 GraspGenX 기본 포트가 다르므로 명령을 섞어 사용하지 않습니다.

    1. 소스 빌드로 서버와 모델 준비¶

    로봇 PC ros_runner/config/runners.yaml의 inference_connection에서 SSH 주소·계정·포트와 모델 포트를 확인합니다. 인증은 호스트 SSH 키/agent를 사용합니다.

    구성 입력 → 출력 배포 소스
    SAM 3 RGB·텍스트/박스 → 마스크 deploy/sam3-docker/
    GraspGenX 객체 XYZ → 파지 자세·점수 deploy/graspgenx-docker/

    GPU runtime·모델 체크포인트·그리퍼 assets를 준비합니다. 각 배포 디렉터리의 .env.example을 복사하고 장비의 GPU·사용자·볼륨·리소스를 지정합니다. 두 모델은 서로 다른 디렉터리에서 각각 빌드·실행합니다.

    # 장비별 빌드·실행 설정 파일의 편집용 사본 생성
cp .env.example .env
# Compose 설정과 환경변수가 올바르게 적용되는지 확인
docker compose config
# 해당 모델의 소스로 Docker 이미지 빌드
docker compose build
# 지정한 모델 컨테이너를 생성하고 백그라운드 실행
docker compose up -d segmentation
# GraspGenX 디렉터리에서는 위 SAM 명령 대신 사용
# docker compose up -d inference

    SAM 배포 소스 · GraspGenX 배포 소스

    모델 포트 맞추기

    ROS 공통 YAML은 SAM 5567·GraspGenX 5566을 사용합니다. SAM Compose 기본 공개 포트는 5567이지만 GraspGenX Compose 템플릿은 5556입니다. 템플릿을 그대로 쓰면 runner의 grasp_remote_port를 서버의 실제 공개 포트 5556으로 맞춥니다. 모델 수신 포트·Docker 공개 포트·SSH 터널·bridge endpoint를 구분합니다.

    컨테이너가 시작되면 모델 서버 명령이 실행됩니다. GPU 가중치 로딩 뒤 health가 성공해야 준비 완료입니다. 기존 서버가 실행 중일 때 같은 Python 서버를 다시 실행하면 포트 충돌이 발생할 수 있습니다.

    2. 상태·로그·시작·종료¶

    각 모델의 Compose 디렉터리에서 실행합니다. 아래는 SAM 서비스 예시이며 GraspGenX에는 segmentation 대신 inference를 사용합니다.

    # 모델 서비스의 실행·정지 상태 확인
docker compose ps -a
# 지정한 모델 서비스의 최근 로그 확인
docker compose logs --tail 100 segmentation
# 기존 모델 서비스 시작
docker compose start segmentation
# 모델 서비스 종료
docker compose stop segmentation
# 모델 서비스 재시작
docker compose restart segmentation

    Compose 외부에서 생성한 컨테이너는 실제 이름으로 docker ps -a, docker logs, docker start/stop/restart를 사용합니다. 실행 정책은 docker inspect로 확인합니다. 저장소 Compose 템플릿만으로 외부 배포의 이미지·재시작 정책을 단정하지 않습니다.

    docker compose logs -f의 Ctrl+C는 로그 보기만 끝냅니다. 컨테이너 내부 확인은 docker compose exec segmentation bash를 사용하며, 셸의 exit는 서버를 종료하지 않습니다. GPU 사용은 서버 호스트의 nvidia-smi로 확인합니다.

    3. 모델 health¶

    서버 호스트의 각 Compose 디렉터리에서 확인합니다.

    # SAM 3 서버에 컨테이너 내부 주소로 health 요청 전송
docker compose exec -T segmentation python -c \
  "from wire import request; print(request('tcp://127.0.0.1:5567', {'action': 'health'}, timeout=5))"
# GraspGenX 서버에 컨테이너 내부 주소로 health 요청 전송
docker compose exec -T inference python /opt/deploy/scripts/health_check.py \
  --endpoint tcp://127.0.0.1:5556

    포트를 바꾼 환경에서는 실제 컨테이너 내부 수신 포트를 지정합니다. SAM health의 backend=sam3, mock=False와 GraspGenX의 정상 응답을 확인합니다.

    4. 로봇 PC 연결¶

    외부 GPU 서버를 쓸 때 SSH 터널 설정을 먼저 구성합니다. runner가 실행한 bridge의 최종 endpoint는 시작 로그에서 확인합니다.

    ROS 컨테이너에서는 다음을 사용합니다.

    # SAM 3 ROS 브리지를 통해 모델 health 확인
ros2 service call /sam3/health std_srvs/srv/Trigger '{}'
# GraspGenX ROS 브리지를 통해 모델 health 확인
ros2 service call /graspgenx/health std_srvs/srv/Trigger '{}'

    서버 내부 health는 성공하지만 ROS health가 실패하면 터널·포트 매핑·bridge endpoint를 확인합니다. 모델 실행은 ROS runner 활성화와 별도입니다.

    5. 변경 반영¶

    변경 반영 방법
    SSH 주소·터널 포트 runner YAML 수정 → 호스트 터널 재시작 → BT 재활성화
    ROS 대상·후보 수 공통 YAML 수정 → BT 재활성화
    모델 코드가 이미지에 복사됨 이미지 재빌드 → 해당 컨테이너 재생성
    모델 파일·서버 설정 볼륨/이미지의 실제 경로 확인 → 모델 재로딩
    Docker 공개 포트·볼륨 Compose 설정 수정 → 컨테이너 재생성

    restart는 기존 이미지와 생성 설정을 재사용합니다. 체크포인트·캐시·로그 볼륨은 컨테이너와 분리해 관리합니다. 컨테이너 안에서 변경한 내용을 이미지·tar.gz로 저장하려면 컨테이너를 다시 이미지로 저장을 참고하세요. 운영 장애는 컨테이너 상태 → 모델 로그 → 서버 health → 터널 → ROS health 순서로 좁힙니다.
